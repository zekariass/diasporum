1.1 Non-negotiable principles
 Backend is authoritative. All access control, category validation, matching eligibility, age gating, capacity enforcement, media access and moderation decisions are enforced in Spring Boot and, where appropriate, PostgreSQL constraints/functions.
 PostgreSQL is the durable source of truth. Ably distributes realtime events but is not the message history store. R2 stores object bytes; PostgreSQL stores metadata and access policy.
 Visibility is separate from classification. A category explains what content is about. A scope determines who can discover it. Categories must never implicitly broaden an audience.
 Least privilege. Diasporum authentication establishes the account identity; scoped platform, community and business roles determine what the account may do within their respective boundaries.
 Private data is not hidden only by the UI. APIs must omit prohibited fields entirely, including original photo URLs for blurred/hidden matchmaking profiles and private address coordinates.
 Reliable async delivery. Persist durable state and outbox events in one database transaction; publish after commit with retries and idempotent consumers.
 Modular monolith first. Keep domain boundaries clear within Spring Boot. Introduce separately deployed services only where operational or scaling evidence justifies it.
 Reviewable and reversible changes. Use versioned migrations, clean staging installs, tested backups and release gates.
1.2 Product rules that shape the architecture
 Exactly one permanent General Chat Room per community. There is no permanent General Voice Room.

4.1 Authorization rules
 Never trust `user_id`, `owner_id`, `role`, `is_verified` or `community_id` supplied by the client as proof of permission.
 Resolve the authenticated principal to `users.id`. Google/Apple provider identities map through `(issuer, subject)` in `external_identities`; local email/password resolves through `users.email_normalized` and `user_credentials`.
 Check object ownership and visibility for every read, update, delete, upload grant, message operation and report action.
 Apply blocks in both directions wherever relevant: People Connect, matchmaking, search, notifications, direct messaging and contact suggestions.
 Use immutable audit entries for role assignment/revocation, moderation action, verification decision and sensitive support access.
 Platform moderators may override user-level protections only through explicit emergency/admin paths that record the actor and reason.

6.3 PostgreSQL deployment model
 Keep PostgreSQL on a private network; only the backend and tightly controlled operations tools can connect.
 Use a supported JDBC driver, connection pool limits, statement/transaction timeouts and migration tool such as Flyway.
 Use separate least-privilege roles for schema migrations and runtime queries. Runtime credentials should not own the schema.
 Enable encrypted transport where traffic crosses a trust boundary; store database secrets outside source control.
 Automate backups and point-in-time recovery where available, and perform restore tests to a separate host.
 Use query plans, slow-query logs, pool saturation and index-use metrics to guide later partitioning or read scaling.
7. Core workflows and transaction boundaries
7.1 Sign-in and profile bootstrap
1. Expo presents Diasporum-native email/password, Google and Apple sign-in. Google/Apple native SDKs return provider identity credentials; Next.js admin uses a secure BFF/session pattern.
2. Spring Boot verifies password credentials or validates the provider ID token signature, issuer, audience, expiry and nonce where applicable. Provider tokens are identity evidence only.
3. Resolve an existing `(issuer, subject)` first. For a new social identity, use verified normalized email only under the v10.12 account-linking assurance rules; map it to `users.id`. Different normalized emails create separate accounts.
4. Create the `users` account first. Create the optional one-to-one `profiles` row when profile onboarding is completed; create settings, privacy defaults and membership in an idempotent transaction.
5. Issue Diasporum access/refresh credentials and, on every request, evaluate account status, profile completion where required, membership, scoped roles, feature eligibility, object visibility and block/moderation state.
7.2 Durable chat message and realtime event
1. Client submits a message to the REST API with an idempotency/client message key.
2. Spring Boot authorises membership/participants, validates content, assigns the next room/conversation sequence number and inserts the message.
3. The same database transaction records an outbox event describing the committed message.
4. After commit, a worker publishes the event to the authorised Ably channel and marks the outbox delivery state.

7.3 Mutual-like matchmaking
1. User activates a matchmaking profile after backend adult eligibility checks and sets discovery preferences.
2. Discovery filters active eligible adults and applies blocks, visibility, verification settings and preference compatibility in both directions.
3. Each user records a directional LIKE or PASS. `matchmaking_swipes` holds the current state; `matchmaking_swipe_history` records each swipe and any reversal as an append-only event.
4. Create one canonical pair match only when both current directional swipes are ACTIVE LIKE. In the same transaction create or reuse the pair's accepted GENERAL direct conversation; do not create follows or a duplicate friendship row. Show the Matched badge while the match remains active.
5. Before a mutual match occurs, a user can cancel their outgoing active LIKE. The backend marks it WITHDRAWN and records LIKE_CANCELLED atomically; a withdrawn LIKE must not create a match.
6. Rewind reverses only the actor's most recent eligible unreversed swipe (including an accidental PASS); the backend marks the current swipe REWOUND and records a REWOUND history event in the same transaction. Arbitrary older swipes cannot be restored.
7. On unmatch, close the matchmaking relationship, restrict future sending according to the match policy, and retain the GENERAL conversation and message history. Do not remove independent follows; the Matched badge disappears. Rematching after unmatch is unsupported by the current policy.
7.4 Voice room join and promotion
1. Client requests to join a room; backend checks room/session status, privacy, invite or discovery permission, account restriction and capacity.
2. Lock or otherwise serialise on the session row, create an active participant record, and enforce `max_participants` before issuing a short-lived RTC token.
3. Listeners request stage access through `voice_room_speaker_requests`; only the active host or an authorised moderator may respond.
4. Approval serialises against other approvals, checks a free stage seat, promotes the participant, assigns a seat and records a moderation/audit event.
5. Demotion releases the seat and returns the participant to listener role. Explicit departure sets `left_at`; a genuine rejoin creates a new participation record. Reconcile provider presence and apply the configured expiry/hostless rules.

8.4 Mixed-feed ordering and view tracking

The default For You feed is a mixed community timeline with a view-aware ordering rule: first eligible content the user has not meaningfully viewed, newest first within that group; then previously viewed eligible content, also newest first. Apply hard eligibility filters first, including country/community scope, membership, blocks, moderation, publication state, expiry/availability and dismissed content. Do not use view status to bypass relevance, safety or content lifecycle rules.
Use `user_content_views`, keyed by user, content type and content ID, for first/last meaningful view time and an optional qualified view count. A card qualifies when at least 50% of its visible area remains in the viewport for approximately one second, or when the user opens its full detail/thread view. Do not mark an item viewed because an API returned it, because it was preloaded, or because it was rendered off-screen. The thresholds are configurable client rules and should be tested on mobile and web.
The view-tracking endpoint should be idempotent and batch-capable. Upsert one row per user/content pair; preserve the earliest first_viewed_at, advance last_viewed_at monotonically, and increment view_count only for a qualified view event after a server-enforced or client-assisted cooldown. Preserve stable cursor pagination and deduplicate candidate IDs across organic and featured pools. Content may reappear after meaningful updates, such as a new reply, event time/location change or job update; avoid repeatedly resurfacing unchanged content.
If a separate Latest mode is offered, it should remain reverse chronological among eligible content rather than being reordered by view status. View-aware ordering belongs to For You/default feed. The horizontal category tabs remain a separate navigation layer into focused Events, Jobs, Property, Vehicles, Business, Polls and Spare Bag experiences.

14.4 LIKE / PASS / mutual match flow
1. User creates and activates a matchmaking profile and supplies a valid birth date and required eligibility confirmation/verification state.
2. Discovery calculates candidates from active eligible adult profiles and excludes self, blocked pairs, suspended/deleted/paused profiles, already-passed profiles and users not mutually preference-compatible.

4. On reciprocal ACTIVE LIKE, the backend creates one canonical match and creates or activates one accepted `direct_conversations` row in a transaction or equivalent idempotent workflow.
5. Before a mutual match, the sender may cancel an outgoing LIKE. Rewind may undo only the latest eligible unreversed swipe. Both actions write the current state and history atomically and are checked against blocks and matches.
6. Either participant can unmatch. The backend marks the match UNMATCHED with closed_at/closed_by/close_reason, closes or disables the linked GENERAL conversation, preserves its history, leaves independent follows untouched, and removes the Matched badge. Rematching after unmatch is not supported.

15.6 Session-scoped ephemeral live comments

Voice comments are session-scoped temporary text messages. Insertion requires a participant in an ACTIVE session; comments remain recoverable during the INACTIVE grace state. PostgreSQL is the source of truth and the transactional outbox publishes comment-created events after commit.
When a session reaches ENDED or EXPIRED, delete its comment rows, discard queued undelivered commentcreated outbox events, publish `VOICE_ROOM_COMMENTS_CLEARED`, and require clients to clear in-memory comments and ignore late created events for that session. A new session always begins with empty comments. The default recovery grace period is 30 minutes; a background worker must reconcile provider state and terminally expire abandoned sessions without expiring the persistent room.
Keep voice moderation actions and audit history separate from ephemeral comments. The clear event does not mean old comments remain queryable: after terminal cleanup, the comment rows are deleted. Test this against concurrent comment writes and session closure; reject new comments once the session is not ACTIVE.

26. Global Shop Marketplace
Version 10.13 introduces the global Shop Marketplace as a separate full-commerce domain. It is designed for multivendor physical-goods sales while retaining Diasporum's mobile-first product model and modular-monolith architecture. This section consolidates the product, UX, domain, data, API, integration, reliability and launch rules. The companion file Diasporum_Shop_Marketplace_Data_Model_v10_13.md defines the proposed 74-table logical inventory and key columns.
26.1 Scope and relationship to existing marketplaces
The Shop Marketplace is distinct from the existing service marketplace. Service Marketplace remains lead/contact based: customers publish service requests and providers gain lead access; there is no booking, checkout or payment for the actual service. Shop Marketplace sells purchasable products and owns cart, stock, checkout, order, payment, shipping, return and refund lifecycles.
The design supports individual and Business Account sellers, multiple shops per legal seller, global product discovery, mixed-seller carts, one customer checkout, separate seller orders, seller-managed fulfilment, Stripe Connect transfers, Shippo shipping integration, discounts, featured placements, reviews, returns and providerbacked tax. Initial design assumes physical goods. Digital goods are deferred until delivery, tax, refund and consumer-rights handling has been separately designed.
26.2 Global market model
The marketplace is country-aware, not community-membership scoped. Reuse `countries`; add `marketplace_country_settings` for controlled market activation and `product_market_availability` for product-level destination eligibility. A country may allow browsing while checkout or seller onboarding remains disabled. A purchase is allowed only when the buyer destination, product eligibility, seller country, payout route, payment currency, shipping route, tax provider and legal operating requirements are all supported.
Diasporum must not claim worldwide seller payment coverage simply because the product is global. Stripe Connect cross-border payout availability is constrained by the platform and connected-account countries; other countries may require an alternative payout provider or a separately approved arrangement. Country enablement is a platform configuration and compliance decision, not an inference from `countries.is_active`.
Use ISO 4217 currency codes and currency-specific minor-unit exponents. `product_variant_prices` stores explicit prices per variant, market country and currency, allowing different prices in countries that share a currency. Each checkout and order uses one currency. No automatic FX conversion is assumed; a currency must have an explicit seller price for the selected market or a separately approved FX quote.
26.3 Seller, shop and permission model
`marketplace_sellers` is the legal seller entity. Exactly one of `owner_user_id` or `business_account_id` is populated. `shops` belongs to a seller; a seller may operate multiple shops. `seller_payment_accounts` associates the legal seller with a connected payment account, so several shops for the same legal seller can share one Stripe connected account.
Individual seller authorisation is derived from the authenticated user. Business seller authorisation reuses `business_account_members` and the existing fixed Java role policies (OWNER, ADMINISTRATOR, EDITOR, LISTING_MANAGER, BILLING_MANAGER). Do not add `shop_members`, generic roles or a database-driven permission matrix in the initial design. Every seller operation derives and authorises the actor server-side.
26.4 Catalogue, categories and product prices
Create one global hierarchical `product_categories` taxonomy with multilingual translations. Keep it separate from Business Directory, Jobs, Service Marketplace and Feed categories. Category attribute definitions specify data type, validation, filterability and whether an attribute applies to product or variant. Product-level flexible attributes may

`product_variants` contains seller-scoped SKU, weight and dimensions. `product_market_availability` controls destination-country eligibility; `product_variant_prices` stores explicit prices per market/currency. 26.5 Inventory and reservations

Track on-hand stock per variant and inventory location. Available quantity equals on-hand quantity minus active, unexpired reservations. Checkout reserves stock transactionally for a short configurable period (initial proposal: 15 minutes). Concurrent reservations must not oversell. Successful payment/order placement converts reservations into confirmed inventory movements; failed, cancelled or expired checkouts release them exactly once. A worker, not a mobile timer, expires reservations.
Stock adjustments, dispatch, cancellations, returns and write-offs create append-only inventory movements. Returns do not automatically restock: seller inspection and disposition rules determine whether an item becomes sellable, damaged or written off.
26.6 Cart, checkout and multi-seller orders

A cart can contain products from multiple shops but has one checkout currency. Checkout validates each variant price for the selected market/currency, product-country availability, stock, seller status, destination/shipping eligibility, discount and tax. Unsupported or missing market price, currency or shipping data must be resolved explicitly; the service must never silently convert currencies, omit a line or assume zero tax.
Checkout quote is an attempt, not yet an order. It snapshots product name, SKU, variant, seller/shop, market/currency price, quantity, shipping quote, discount, tax calculation and policy versions. Shipping and freeshipping thresholds are calculated independently per seller; a seller's threshold uses only that seller's eligible items.
When the buyer confirms checkout, create the `orders` parent and one `seller_orders` row per shop with `PAYMENT_PENDING`, plus immutable `order_items` and address/price/shipping/discount/tax snapshots. Create and associate the Stripe PaymentIntent idempotently. A verified payment-success webhook finalizes the order to `PLACED` and confirms inventory reservations/stock movements. Failed or expired payment cancels pending orders and releases reservations exactly once. This avoids a circular payment/order reference. Each seller order then advances independently; dispatch by Seller A does not change Seller B's fulfilment status. The buyer sees one parent order with separate progress and shipment details for every seller.
26.7 Stripe Connect and commerce money flow

Stripe Connect is the initial payment-provider candidate. Use server-generated hosted onboarding links and a connected account for each legal seller where the selected Stripe country/capability arrangement allows it. The Expo app opens the single-use onboarding URL in the system browser and returns through an app/universal link. The return URL is not proof of verification: Diasporum refreshes account status through its backend and signed webhooks. Persist the connected-account ID, requested capabilities, charges/payout status and requirements summary; never store identity documents or bank credentials in the Diasporum database.

For a mixed-seller checkout, the proposed flow is one platform PaymentIntent/charge followed by separate transfers to each seller's connected account. Diasporum calculates each seller allocation and commission; Stripe performs the transfer. Associate transfers with the parent order using transfer-group/source-charge references where supported. Persist payment, transfer, reversal, refund, dispute and payout identifiers separately. A failed transfer must not cause a second customer charge.

A transfer moves funds from the platform balance to a connected-account balance; a payout moves funds from that connected account to the seller's bank. They are separate states. Connect is not escrow. The proposed default is transfer when the customer charge has succeeded and funds are eligible/available, subject to final Stripe and legal

26.8 Global tax model
Use a provider-backed tax integration, initially evaluating Stripe Tax, behind a Tax Provider adapter. Keep the dedicated tax persistence small: `tax_registrations`, `tax_calculations`, `tax_calculation_lines`, `tax_liability_records`, `tax_documents`, `tax_document_lines` and `tax_provider_configurations` (seven tables). Provider webhooks are deduplicated in `marketplace_webhook_events`; a separate tax-only event table is not initially required.
The provider may calculate tax for a transaction, but it does not automatically settle the legal question of whether the seller or marketplace is liable. That liability is established and approved per jurisdiction/business model and snapshotted in `tax_liability_records`; amounts, rates, jurisdictions and tax types are stored in `tax_calculation_lines`. Multiple tax components may apply to one item. If tax calculation or liability configuration is unavailable, checkout fails closed; Diasporum must not silently apply zero tax. Tax calculation is not equivalent to tax registration, invoice issuance, filing or remittance.
26.9 Shipping, Shippo and returns logistics
Each seller configures shipping zones and methods: flat rate, weight based, free, free above threshold, Shippo calculated or seller-managed external carrier. One seller order can have multiple shipments; each shipment can contain multiple packages and partial quantities of an order item. Store parcel weight/dimensions, carrier, tracking, labels and event history. The `shipments` lifecycle supports OUTBOUND and RETURN types, so return parcels do not require a duplicate shipment system.
Shippo is used only where the selected route/carrier/service is available. Rate quote, label purchase and tracking events are provider operations and must be persisted idempotently. Seller-managed external shipping records a validated carrier and tracking reference without claiming a Shippo label was purchased. International customs declarations, HS codes, commercial invoices, restricted goods and import duties require explicit policy and country launch approval.
26.10 Promotions, featured placements, reviews and moderation
Use `marketplace_promotions`, product/category joins, discount codes and redemptions for campaigns. Snapshot discounts and identify whether seller, platform or both funded them. Reuse `featured_items`, `featured_placement_rules` and impressions for SHOP and PRODUCT after extending the allowed content-reference type; do not create duplicate featured-shops/products tables. Use the existing Billing entitlement/product engine for paid promotions if enabled.
Product reviews link to eligible purchased order items; shop reviews link to an eligible seller order. Reuse `reports`, `moderation_actions` and `audit_logs`, adding approved shop/product/review target types. Reuse Messaging with new SHOP, SHOP_PRODUCT and SHOP_ORDER contexts, and reuse existing notification/outbox delivery with marketplace event types.
26.11 Mobile navigation and Seller Workspace
Marketplace is a buyer-facing mobile surface for discovery, product detail, cart, checkout, orders, wishlists, reviews and seller contact. Seller Workspace is a separate management area entered from Profile, not a new bottom tab and not the same as Business Workspace. It includes overview, shop selector, products, inventory, orders, shipping, earnings/transfers/payouts, promotions, returns, reviews, settings and Connect onboarding. Multiple shops are switched within the workspace. Business-owned shop permissions reuse Business Account membership and policies.

Add a `shopmarketplace` root module in the Spring Boot modular monolith. It owns catalogue, seller, inventory, cart/checkout, orders, shipping, returns and marketplace financial records. 26.16 Reliability and financial invariants
 One parent order may have multiple seller orders; seller fulfilment, shipping, return and transfer statuses remain independent.
 Money is always stored with currency. Do not aggregate different currencies without an explicit FX conversion record.
 Order, price, address, shipping, discount, commission and tax snapshots are immutable after placement except audited corrections.
 Inventory reservations, checkout, discount redemption, refunds, transfer creation and ledger postings are concurrency-safe and idempotent.
 Payment, seller transfer, transfer reversal and bank payout are separate records and statuses. A failed transfer never triggers a second customer charge.
 Ledger journals balance per currency; posted entries are append-only. Provider state is reconciled against internal orders and ledger.
 Webhook authenticity is verified before processing; duplicate and delayed events cannot duplicate payment, label, inventory or notification effects.
 Private dispatch/customer addresses are only exposed to authorised fulfilment actors and are never included in public discovery DTOs.

Appendix D. Historical v10.0 updates: marketplaces, visibility and billing

This section records the product decisions added after the v9.0 baseline. The companion SQL is Diasporum_PostgreSQL_Schema_v10.sql. V10 is a clean-install candidate based on v9.0, not an in-place migration. Pricing and quotas below are configurable examples, not final commercial commitments.
D.1 Property marketplace (historical)
Property listings support SALE and RENT with a full description, exact decimal price and currency, optional rent period, bedrooms, bathrooms, reception rooms, floor area and unit, furnished status, rental deposit, bills included, minimum tenancy, availability date, tenure/condition, public location, contact preferences, ordered media, amenities, saves, moderation and expiry. No online booking, checkout, escrow or transaction processing is included. In v10.5, additional category-specific attributes are stored in an object-shaped JSONB column and validated by the backend; high-value filter fields remain dedicated columns.
Property types use a canonical property_types catalogue mapped through country_property_types. Each country controls which types are enabled and the local display label. A property listing references the country/type pair so a type cannot be used outside its configured country.
D.2 Vehicle marketplace (historical)
Historical v10.0 note: vehicle listings supported SALE and RENT, with relational make/model catalogues and optional variants. The current v10.6 vehicle fields retain separate model_year and registration_year, plus drive_type, previous_owners and JSONB additional_attributes. No insurance_group is included.
D.3 Listing ownership and Business Accounts
Both personal users and Business Accounts can publish eligible property, vehicle, event and job listings. Each listing has one ownership context: personal owner or business account. created_by_user_id records the acting user. Public business profiles belong to a Business Account; one account can manage multiple profiles and locations under one account-level business subscription. The account supports owner, administrator, editor, listing-manager and billing-manager roles. Payment does not automatically verify a business.
D.4 Shared country-bounded visibility
The common visibility modes are COMMUNITY, SELECTED_COMMUNITIES and COUNTRY. COMMUNITY targets one community; SELECTED_COMMUNITIES targets an explicit list of communities; COUNTRY targets eligible users across the selected country. The country is the hard upper boundary: UK content must not be visible through US discovery. Selected communities must have the same destination country as the listing/profile. Backend authorization must enforce the same rule for search, direct links, saved items, recommendations, notifications and media access. Scope is separate from content category and physical location.
The visibility model applies to feed posts, events, jobs, business profiles/listings, property listings, vehicle listings and matchmaking profiles. Classification is independent from audience scope; audience scope never expands because of a category or paid promotion.
D.5 Configurable billing model
Billing is centralised and entitlement-driven. Plans grant ongoing feature permissions and quotas; one-time products grant a specific action/credit or time-limited benefit; usage records track quota consumption where required. Feature modules ask the central entitlement service whether an action is allowed and do not implement their own payment logic.
Illustrative personal plans: FREE, SILVER and GOLD. Illustrative business plans: BUSINESS_FREE, BUSINESS_SILVER and BUSINESS_GOLD. The business subscription belongs to the Business Account, not each public business profile. A personal account may manage a business account without its personal plan being replaced. A listing purchase can be purchased independently of a subscription if configured. Listing publication and featured promotion are distinct products.

E.1 Address normalization (Option A)
Property listings, vehicle listings, events and job listings no longer duplicate city/region/postcode values when they reference a shared addresses row. This update extends the v10.2 baseline with an explicit feed-ranking strategy, separate featured-placement records, reusable per-user content view tracking and optional impression analytics. F.1 View-tracking data contract
`user_content_views` stores one row for each `(user_id, content_type, content_id)`. The supported typed references in v10.6 are FEED_POST, EVENT, JOB, PROPERTY, VEHICLE, BUSINESS and SPARE_BAG_LISTING. The row records first_viewed_at, last_viewed_at and view_count. It is not an impression log: one view row is retained per user/content pair, and `view_count` advances only for qualified view events under a defined cooldown/idempotency policy.
The client reports visibility only after the configured viewport threshold (initial proposal: at least 50% visible for about one second) or when the full item/thread is opened. Appendix H. v10.6 billing quota behaviour and deferred feature
H.1 Direct-message send quota
The current billing feature is DIRECT_MESSAGE_SEND. It counts outgoing direct messages successfully accepted by the service, not conversation starts. The quota scope is PER_RECIPIENT: the same sender has a separate allowance for each recipient, and messages to that recipient across multiple conversations share the allowance. Incoming replies do not consume the sender's quota.
For each accepted outgoing message, write an idempotent billing_usage_records usage unit in the same service transaction as message acceptance, with user_id set to the sender, target_type set to USER and target_id set to the recipient profile ID. Do not count failed sends, duplicate retries, inbound messages or opening a conversation. Use the target-specific usage index for checks. A sender's allowance to Alice must not affect the allowance to Bob.
H.2 Plan-configurable limit and reset period
Configure quantity_limit and reset_period on billing_plan_entitlements for each plan. Supported reset periods are DAY, WEEK, MONTH, YEAR, SUBSCRIPTION_PERIOD and NEVER. The reset window must be resolved from the active plan entitlement; application code must not hard-code the window. The schema requires a reset_period whenever quantity_limit is non-NULL. billing_features.reset_period is NULL for DIRECT_MESSAGE_SEND because the effective period is plan-specific.
When the entitlement is enabled, quantity_limit = NULL means unlimited usage; quantity_limit = 0 means no usage is permitted; a positive number is the maximum outgoing-message count per sender-recipient pair for the configured reset window. An entitlement with enabled = false denies the feature regardless of quantity_limit. If no applicable plan entitlement is configured, the backend must fail closed rather than infer a default. The schema does not seed an arbitrary quota or reset period; administrators must configure and test the intended free and paid plan values before enabling billing enforcement.
When a user reaches the configured limit, do not silently charge them. Return a clear entitlement/paywall response and allow messaging only after the user has an eligible subscription or completes an explicitly confirmed, supported purchase. Verify billing events using the trusted server-side billing flow and make the usage/purchase operation idempotent.
H.3 Deferred feature -- SAVE_CONTENT
SAVE_CONTENT is recorded as a future requirement for normal/personal users to save or bookmark supported content such as feed posts, property listings, vehicle listings and other approved content types. It is deliberately not included in the v10.6 billing feature catalogue or schema. Add it only in a later approved schema update.

Appendix M. v10.11 Community Help & Offers
This appendix is the authoritative Community Help & Offers addition to v10.11. It is a structured feed feature for informal assistance, donations, language practice, newcomer support and volunteering--not a separate marketplace. Paid professional services remain in the Service Marketplace. The database adds one lifecycle table and reuses existing feed, taxonomy, moderation, notifications and messaging infrastructure.
M.1 Product and scope decisions
 A Community Help item is a feed_posts row with post_type = COMMUNITY_HELP. The parent row remains the source of truth for author, community, country/audience, title/body, media, comments, reactions, publication, moderation and reports.
 There are two kinds: REQUEST (the author needs assistance) and OFFER (the author offers informal, unpaid assistance or donations). Categories can include Items & Donations, Practical Assistance, Language & Learning, Newcomer Support and Volunteering, configured per country.
 Community Help posts can appear in the dedicated Community Help section and optionally as normal cards in the main Feed. Do not create a second social graph, dedicated comment/reaction tables, payment workflow or separate chat system.
 Paid cleaning, babysitting, plumbing, tutoring or other professional services remain in servicemarketplace when charged as professional work. The Community Help feature is for informal assistance and volunteering.
M.2 Database changes
 Add COMMUNITY_HELP to feed_posts.post_type. All usual feed audience, content status, comments, reactions, media, blocks and moderation rules still apply. Create the post as DRAFT; do not directly publish a help post before its lifecycle row exists.
 Extend category_module with COMMUNITY_HELP. Administrators configure country_categories and map them in country_category_modules with module_key = COMMUNITY_HELP. validate_feed_post_country_category() uses the COMMUNITY_HELP module for this post type and FEED for other feed post types.

M.3 Lifecycle and database integrity
 Creation workflow: insert feed_posts as DRAFT; insert community_help_posts with help_status = OPEN in the same transaction; then use the standard publication/moderation flow. The schema rejects publication without lifecycle metadata and rejects lifecycle metadata attached to a non-COMMUNITY_HELP parent.
 feed_posts.status controls publication/moderation. community_help_posts.help_status controls help availability. They are separate state dimensions.
 Supported transitions: OPEN  PAUSED and OPEN/PAUSED  RESOLVED, CLOSED or EXPIRED. RESOLVED, CLOSED and EXPIRED are terminal. help_kind, post_id and author identity are immutable. resolved_at/closed_at/expired_at are set by the database on state changes, not directly by client payloads.

Appendix N. v10.12 first-party authentication and account identity

This appendix supersedes v10.11 statements that designate Keycloak/Authentik as the runtime identity authority, map provider subjects directly to profiles, or use the database-driven business rolepermission matrix. All other v10.11 product features remain carried forward unless this appendix explicitly changes them.
N.1 Account identity and profile separation

`users` is the permanent Diasporum account identity. It owns the immutable account UUID, one primary email, normalized email, email-verification state, account status and account lifecycle timestamps. `profiles` is an optional one-to-one extension for public and personal profile attributes. `profiles.id` is both its primary key and a foreign key to `users.id`; the UUID is shared, not duplicated.
A user can register, authenticate and hold a session before completing onboarding. The profile row is created when the user supplies required profile information (display name and origin/current country). Move `account_status` and account `deleted_at` to `users`; keep username, display name, bio, countries, city, date of birth, age eligibility, trust score and profile completion on `profiles`. Feature flows that require a completed profile must check for it explicitly.
Every account, actor, membership, ownership, audit, session and role foreign key should reference `users.id`. Profile-only relationships should be explicit and reference `profiles` only when the presence of profile details is itself required. This is a v10.12 identity-root change, not a cosmetic table addition.

N.5 Password, token and session controls

 Hash passwords with Argon2id using a PHC-encoded value. Use the OWASP Password Storage Cheat Sheet baseline of at least 19 MiB memory, two iterations and parallelism one as a minimum; benchmark production parameters and increase them where capacity allows. Never store plaintext passwords or reversible password encryption.
 For password-only authentication, require at least 15 characters, permit at least 64 characters, avoid arbitrary composition rules, and reject common/compromised passwords. Follow NIST SP 800-63B-4 password-length and verifier guidance.
 Use short-lived asymmetric-signed access JWTs (initial target 10-15 minutes), with explicit issuer, audience, subject=users.id, session ID (sid), token ID (jti), issue/expiry timestamps and signing-key ID (kid). Publish public verification keys through JWKS and rotate private signing keys safely.
 Use cryptographically random opaque refresh tokens (at least 256 bits). Store only SHA-256 hashes. Rotate on each use; retain consumed-token lineage; on replay, revoke the token family/session and require fresh authentication. Serialise concurrent refreshes. Initial policy: 30-day refresh-token lifetime with a 90-day absolute session lifetime; reauthentication is required at absolute expiry. This rotation and replay-detection design follows RFC 9700.
 Use device-specific sessions. Validate the session ID (sid) against active session state on protected requests, using a shared cache or database-backed check, so logout and revocation take effect before the access JWT expires. Revoke sessions on logout, logout-all, password reset/change, account suspension/deletion and detected compromise. Account status changes also revoke active sessions/refresh tokens in the database.
 Expo stores refresh tokens in OS-backed secure storage; keep access tokens in memory where practical. Next.js admin uses a BFF with HttpOnly, Secure, SameSite cookies and CSRF protection; no long-lived browser token in localStorage.
 Email-verification and password-reset tokens are random, single-use, short-lived and stored as SHA-256 hashes. Use generic responses to prevent account enumeration.
 Rate-limit by IP and account identifier with a shared/distributed limiter, progressive delay and abuse detection; do not create a durable login_attempts table solely for throttling.
 Require MFA/step-up for privileged platform staff before production access. Passkeys/WebAuthn or TOTP plus hashed one-time recovery codes are appropriate options; deliver authenticator enrollment/storage in a dedicated security implementation milestone and do not enable privileged production accounts before it is complete.
 Use audit_logs for role changes, identity linking/unlinking, sensitive support access, password/security changes and administrative actions; never log passwords, raw tokens or full provider credentials.
